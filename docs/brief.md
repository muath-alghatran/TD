# جزء (أ) — ملاحظتان صريحتان قبل التنفيذ

قلت إنك لا تريد أخطاء. أصدق ما أقدمه لك هو أن أشير إلى نقطتين في التدفق الذي وصفته ستسبّبان مشكلة لو نُفّذتا حرفياً — مع حل كل منهما.

## الملاحظة الأولى: لا تطلب الماركة بعد رقم الهيكل

**ما وصفته:** رقم الهيكل ← رسم السيارة ← ثم خيار الماركة ← ثم المركبات الخاصة بالماركة.

**المشكلة:** رقم الهيكل *يحتوي أصلاً* على الماركة والموديل والسنة والفئة والمحرك. لو سألت العميل عنها بعده، فأنت تطلب منه معلومة أعطاك إياها للتو — وهذا يُشعره أن النظام لم يفهمه، وهو أسوأ انطباع أول ممكن.

**الحل المعتمد في النموذج:**

```
مسار (1) — العميل يملك رقم الهيكل  [المسار الرئيسي]
   رقم الهيكل ← فك تشفير ← بطاقة تأكيد: "تويوتا كامري 2021 — 2.5 لتر GLE"
   ← [تأكيد]  أو  [ليست سيارتي ← تعديل يدوي]
   ← مباشرة إلى المخطط

مسار (2) — العميل لا يملك رقم الهيكل  [المسار البديل]
   الماركة ← الموديل ← السنة ← (الفئة إن لزم) ← المخطط
   مع تنبيه: "بدون رقم الهيكل قد تختلف بعض القطع بين الفئات"
```

اختيار الماركة يبقى موجوداً كما أردت — لكن **كمسار بديل، لا كخطوة تالية**. النتيجة نفسها، والتجربة أذكى بمرتين.

## الملاحظة الثانية: مستحيل عرض "جميع القطع" على رسم واحد

**ما وصفته:** رسم مبسط للسيارة بجميع القطع مع أرقامها ومسمياتها.

**المشكلة:** السيارة الواحدة فيها ما بين ٢٥٠٠٠ و٣٠٠٠٠ قطعة. أي محاولة لعرضها في مخطط واحد تنتج شاشة غير قابلة للاستخدام، خصوصاً على الجوال.

**الحل المعتمد — مخطط بثلاث طبقات:**

```
الطبقة 1 · مخطط السيارة        →  8 مناطق فقط، كل منطقة نقطة ملوّنة
الطبقة 2 · فلتر التصنيف         →  بدي · ميكانيكا · كهرباء · عفشة وفرامل
الطبقة 3 · قائمة قطع المنطقة    →  رقم OEM + المسمى + السعر + حالة التوفر
```

هذه ليست تنازلاً عن فكرتك — هي **تنفيذها الصحيح**. ثمانِ نقاط واضحة أفضل من ثلاثمئة نقطة متراكبة، والعميل يصل للقطعة في ثلاث ضغطات.

### والابتكار الذي يميّزك فعلاً

في النموذج المرفق نفّذت شيئاً لا يفعله أي منافس في السوق السعودي ولا حتى كتالوجات الوكالات العالمية:

> **كل نقطة على المخطط ملوّنة بحالة توفرها قبل أن يضغط عليها العميل.**
>
> 🟢 أخضر = متوفر ومؤكد · 🟡 أصفر = يحتاج تأكيد المورد · ⚪ رمادي = طلب خاص

العميل يفتح المخطط فيرى **بنظرة واحدة** أين يجد ما يحتاجه فوراً. محرك الوعد لم يعد رقماً مخفياً في صفحة القطعة — صار لغة بصرية تحكم الشاشة كلها.

وقاعدة التصميم المشتقة من ذلك: **اللون في هذا الموقع يعني التوفر ولا يعني شيئاً آخر.** لا ألوان زخرفية، لا تدرجات، لا أزرار ملونة للتزيين. الواجهة كلها بترولي ورمادي، واللون المشبع الوحيد على الشاشة هو حالة القطعة. هذا يجعل المعلومة الأهم غير قابلة للتفويت.

> عائلة IBM Plex صُمّمت أصلاً للسياق الهندسي والتقني، وعربيتها ولاتينيتها من مصدر واحد — وهذا سبب الاختيار، لا الصدفة.

**قاعدة الأرقام:** بيانات الآلة (أرقام القطع، النسب، الإحداثيات) بأرقام لاتينية أحادية المسافة. سرد الإنسان (عدد الأيام، عدد القطع، مدة الضمان) بأرقام عربية-هندية `٠١٢٣٤٥٦٧٨٩`. التمييز مقصود ويجب الالتزام به.

**عناصر اللغة البصرية**
- **علامات التسجيل** في زوايا كل لوح — مقتبسة من الرسم الهندسي، لا زخرفة
- **مسطرة إحداثيات** `A–H` × `1–4` حول المخطط، وكل موضع له مرجع (`C4`) — كصفحة كتالوج قطع حقيقية
- **حواف حادة** (`border-radius: 2–3px`) في كل مكان عدا عناصر الحالة الدائرية
- **دوائر الاستدعاء** المرقّمة تربط المخطط بقائمة القطع بصرياً

**الحركة — مبررة لا مزخرفة**
- **رسم المخطط عند التحميل:** خطوط SVG تُرسم تدريجياً عبر `stroke-dasharray` + `pathLength="1"` بتتابع زمني — كراسمة مخططات تنفّذ لوحة. هذه هي اللحظة المميزة الوحيدة في الموقع.
- عُقد المواضع تستقر بعد اكتمال الرسم بتتابع `55ms`
- **مقياس الثقة** يمسح إلى قيمته ويعدّ الرقم تصاعدياً
- `prefers-reduced-motion` يُلغي كل ما سبق فوراً — مُنفَّذ في النموذج

**العنصر المميز:** حقل الحبر الذي يحمل المخطط بعُقده المضيئة بحالة التوفر، ومعه مقياس الثقة الدائري. هذه اللحظة الواحدة تحمل كل جرأة التصميم — وكل ما حولها هادئ ومنضبط عمداً.

## 4. محرك الوعد — المنطق الملزم

> نفّذه كوحدة مستقلة `lib/promise-engine.ts` قابلة للاختبار. لا تنثر منطقه في المكوّنات.

```typescript
type Status = 'ok' | 'wait' | 'special';

interface PromiseResult { days: number; confidence: number; status: Status; }

function calcPromise(part, city, mode: 'ship' | 'fit'): PromiseResult {
  // أيام التجهيز
  const prepDays =
      part.stockInternal > 0 ? 0          // بمخزن TD → جاهز فوراً
    : part.supplierReliability >= 0.55 ? 2 // عند مندوب موثوق
    : 5;                                   // طلب خاص

  const shipDays = mode === 'fit' ? 0 : city.shipDaysMax;
  const fitDays  = mode === 'fit' ? 1 : 0;   // موعد التركيب
  const days     = Math.max(1, prepDays + shipDays + fitDays);

  // نسبة الثقة
  const base =
      part.stockInternal > 0 ? 0.99
    : part.supplierReliability >= 0.55 ? part.supplierReliability
    : 0.50;

  const confidence = base * (mode === 'fit' ? 1.0 : city.trustFactor);

  const status = confidence >= 0.85 ? 'ok'
               : confidence >= 0.65 ? 'wait'
               : 'special';

  return { days, confidence, status };
}
```

**قواعد صارمة:**
- العتبات (`0.85` / `0.65`) وأيام التجهيز ونسبة الخصم **تُقرأ من جدول الإعدادات في قاعدة البيانات**، لا تُكتب في الكود. المالك يعدّلها دون نشر جديد.
- الحالة الرمادية **لا تعرض تاريخاً محدداً أبداً**. النص الوحيد: «نؤكد لك التوفر خلال ٢٤ ساعة».
- كل حساب وعد يُسجَّل مع الطلب (`promisedDays`, `confidenceAtOrder`) — لأننا سنقارن الوعد بالفعل لاحقاً.

## 6. سجل الطلب المفقود — مطلوب من اليوم الأول

سجّل في `DemandGap` **كل** واحدة من هذه الحالات، تلقائياً ودون تدخل:

| الحدث | القيمة المسجّلة |
|---|---|
| بحث لم يُرجع نتائج | نص البحث كما كتبه العميل حرفياً |
| قطعة غير مغطاة للسيارة | رقم OEM + بيانات السيارة |
| ضغط «أبلغني عند التوفر» | القطعة + المدينة |
| مغادرة صفحة قطعة رمادية دون طلب | القطعة + المدينة |
| إلغاء طلب رمادي لعدم التوفر | القطعة + السبب |

**هذا ليس تحليلات — هذا أصل استراتيجي.** بعد ٢٤ شهراً ستحدد هذه البيانات أي قطع تُصنَّع. لا تؤجّلها إلى نسخة لاحقة.

## 7. المزامنة مع ملف الإكسل

المصدر: Google Sheets بنفس بنية `TrustDrive_Parts_Master.xlsx`.

- مزامنة تلقائية كل **15 دقيقة** + زر «مزامنة الآن» في لوحة التحكم
- المزامنة تكتب في قاعدة البيانات — **الزوار يقرأون من قاعدة البيانات لا من الشيت**

**قواعد الحماية (إلزامية):**
1. `SKU` هو المفتاح الوحيد وغير قابل للتغيير
2. صف بلا SKU يُتجاهل ولا يوقف المزامنة
3. **فرق سعر > 40٪ → لا يُطبَّق تلقائياً**، بل ينتظر موافقة يدوية *(يحميك من بيع قطعة بـ٢٠ ريال بدل ٢٠٠٠ بسبب خطأ إدخال)*
4. قطعة تُحذف من الشيت → تُخفى من الموقع ولا تُحذف من القاعدة
5. كل مزامنة تُسجَّل في `SyncLog`
6. فشل المزامنة → تنبيه واتساب فوري للمالك

## 9. معايير القبول — لا يُسلَّم المشروع قبل اجتيازها كاملة

**الوظيفة**
- [ ] رقم هيكل صحيح يُظهر السيارة الصحيحة · رقم خاطئ يُظهر رسالة واضحة لا شاشة فارغة
- [ ] المسار اليدوي يصل لنفس النتيجة
- [ ] تغيير الطبقة يعتّم المناطق غير المطابقة ولا يخفيها
- [ ] تغيير المدينة يعيد حساب الأيام والثقة **فوراً** دون إعادة تحميل
- [ ] خيار التركيب يعرض قيمة الخصم بالريال، ولا يُطبَّق إلا على أجرة اليد
- [ ] الحالة الرمادية تحجز المبلغ ولا تسحبه — **اختبر هذا فعلياً ببطاقة حقيقية**
- [ ] فك الحجز التلقائي بعد ٢٤ ساعة عند عدم التأكيد
- [ ] كل بحث فاشل يُسجَّل في `DemandGap`

**البيانات**
- [ ] تعديل سعر في الشيت يظهر في الموقع خلال ١٥ دقيقة
- [ ] تغيير سعر بأكثر من ٤٠٪ يُحجز للموافقة ولا يُطبَّق
- [ ] تعديل عتبة الثقة من الإعدادات يغيّر ألوان الموقع فوراً

**الجودة**
- [ ] Lighthouse ≥ 90 (جوال)
- [ ] التنقل بالكيبورد كامل مع مؤشر تركيز ظاهر على نقاط المخطط
- [ ] قارئ شاشة ينطق اسم المنطقة وحالتها
- [ ] `prefers-reduced-motion` يوقف كل الحركة
- [ ] الفاتورة متوافقة مع ZATCA وتُختبر على بيئة الاختبار الرسمية

**الأمان**

# جزء (ج) — الخطة الزمنية من الصفر إلى التطبيقات

## المرحلة 0 · التحضير (أسبوعان)
تجهيز البيانات الحقيقية قبل أي برمجة:
- ٢٠٠–٣٠٠ قطعة **تويوتا فقط** بأرقام OEM صحيحة ومراجَعة
- جدول التوافق (أي قطعة لأي موديل وسنة) — راجعه مرتين
- اتفاق مكتوب مع ٣–٥ مناديب بأوقات توريد واقعية
- **قياس نسبة التزام كل مندوب فعلياً لأسبوعين قبل الإطلاق** — لأن محرك الوعد يبني عليها

> ابدأ بماركة واحدة. التوسع سهل، وإصلاح كتالوج خاطئ مكلف جداً.

## المرحلة 1 · البناء (٦–٨ أسابيع)
| الأسبوع | المخرَج |
|---|---|
| 1–2 | قاعدة البيانات · المزامنة · لوحة التحكم الأساسية |

| 7 | الدفع (بشقّيه) · الفوترة · واتساب |

**تسليم أسبوعي على رابط تجريبي.** لا تقبل «اختفاء» ثمانية أسابيع ثم تسليم واحد.

## المرحلة 2 · الفحص (٣ أسابيع)
1. **أسبوع داخلي:** أنت وفريقك تنفّذون ٥٠ طلباً وهمياً يغطون كل حالة (أخضر/أصفر/رمادي × توصيل/تركيب × ٥ مدن)
2. **أسبوع مغلق:** ٢٠–٣٠ عميلاً حقيقياً (أقارب وعملاء المركز الحاليين) بطلبات حقيقية ودفع حقيقي
3. **أسبوع إصلاح:** معالجة كل ما ظهر، وإعادة الفحص

**بوابة العبور للإطلاق — لا تطلق قبل تحققها:**
- ✅ نسبة الالتزام بالوعد ≥ ٨٥٪ في الأسبوع المغلق
- ✅ صفر أخطاء تسعير
- ✅ صفر أخطاء توافق (قطعة لسيارة خاطئة)
- ✅ الحالة الرمادية تحجز ولا تسحب — مؤكدة عملياً

## المرحلة 3 · الإطلاق والتشغيل (الشهر ٣–٩)
- إطلاق للرياض والمدن الكبرى
- **مراجعة أسبوعية لثلاثة أرقام فقط:** نسبة الالتزام بالوعد · أعلى ١٠ في الطلب المفقود · نسبة المرتجعات

- إضافة ماركة جديدة كل شهرين

## المرحلة 4 · التطبيقات (بعد ٩ أشهر — بشرط)

> **لا تبنِ التطبيق قبل تحقق هذه الشروط الثلاثة:**
> 1. الموقع مستقر ٣ أشهر متصلة دون خلل حرج
> 2. نسبة الالتزام بالوعد ≥ ٩٠٪
> 3. ≥ ٣٠٪ من زياراتك متكررة (دليل على وجود عملاء أوفياء يستحقون تطبيقاً)

**ما يبرر التطبيق (وإلا فهو نسخة مكررة بلا قيمة):**

# جزء (هـ) — تحذيرات تشغيلية

- **ابدأ بوعود متحفّظة.** قل ٤ أيام وسلّم في ٣. الوعد المخلَف مرتين ينهي سمعتك، ولا يوجد تسويق يصلحها.
- **دقة جدول التوافق قبل حجم الكتالوج.** ٢٠٠ قطعة صحيحة أفضل من ٢٠٠٠ فيها ٥٠ خطأ.
- **لا تنافس بالسعر.** ستخسر أمام من يبيع بالخسارة. نافس بالوعد والضمان والتركيب — وهي أشياء لا يستطيع المتجر الإلكتروني تقليدها لأنه لا يملك ورشة.
- **الفجوة النقدية هي القاتل الصامت.** تدفع للمناديب كاش وتحصّل من الشحن متأخراً. جهّز رأس مال تشغيلي كافياً — مشاريع ناجحة تجارياً سقطت بسبب هذه الفجوة وحدها.
- **راجع مع مختص:** متطلبات ZATCA وأنظمة التجارة الإلكترونية وتراخيص بيع قطع الغيار وشروط الضمان قد تتغير. هذه الوثيقة تقنية وتشغيلية — وليست استشارة قانونية أو محاسبية.
- **قبل لقاء الأساتذة:** اذهب إليهم بالنموذج التفاعلي مفتوحاً على جوالك، ومعه بيانات ٥٠ طلباً حقيقياً. خمسون طلباً حقيقياً أقنع من خمسين شريحة عرض.
